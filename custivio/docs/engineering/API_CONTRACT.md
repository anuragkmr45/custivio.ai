# Custivio API Contract

This contract describes the Fastify API implemented for frontend development. The active backend implementation is `apps/api/src/routes/**`, with business validation in `packages/core/src/**` and `packages/auth/src/**`.

Last updated: 2026-05-17. Source of truth: Fastify route modules in `apps/api/src/routes/**`,
OpenAPI schemas in `apps/api/src/openapi/schemas.ts`, and backend completion audit
`docs/engineering/BACKEND_DB_INFRA_FINAL_READINESS_AUDIT_AFTER_COMPLETION.md`.

## Client Defaults

- Fastify API base URL in local dev: `http://localhost:3000` unless `API_PORT` is set.
- If another local service is already using port `3000`, run the API with an override such as:
  `API_PORT=3002 APP_BASE_URL=http://localhost:3002 pnpm start`.
- Auth: browser session cookie named `custivio_session`; frontend code should call APIs with `credentials: "include"`.
- JSON requests: send `Content-Type: application/json` and `Accept: application/json`.
- Multipart upload requests: use `FormData`; do not set `Content-Type` manually.
- Dates: ISO 8601 strings.
- IDs: UUID strings unless stated otherwise.
- Server-owned fields: `id`, `tenantId`, `createdAt`, `updatedAt`, audit fields, object keys, and status defaults.
- Response request ID: most JSON errors include `x-request-id` response header and `error.requestId`.

## Error Shape

All handled JSON API errors use:

```json
{
  "error": {
    "code": "invalid_asset_input",
    "message": "assetTypeId is required.",
    "requestId": "req_..."
  }
}
```

Common status codes:

| Status | Meaning                                                       | Frontend behavior                                         |
| -----: | ------------------------------------------------------------- | --------------------------------------------------------- |
|    400 | Invalid request body, missing field, bad enum/date/json       | Show field or form error.                                 |
|    401 | Missing/expired session or invalid login                      | Redirect to login.                                        |
|    403 | Authenticated but permission denied                           | Show access denied state.                                 |
|    404 | Entity or resource not found                                  | Show not found/refresh state.                             |
|    409 | Business conflict, duplicate/in-use/locked/insufficient stock | Show conflict message and let user retry after resolving. |
|    429 | Login rate limit                                              | Show retry-after message.                                 |
|    500 | Unexpected server error                                       | Show generic error with request ID.                       |

## Idempotency And Rate Limits

Retry-sensitive mutations support stable idempotency behavior where documented by request body.

- Repeating the same `idempotencyKey` with the same request payload returns the existing result for stock movements, import previews, and export jobs.
- Repeating the same `idempotencyKey` with a different payload returns `409 idempotency_conflict`.
- The frontend should generate a unique idempotency key for double-click-prone workflows such as stock movement, import job creation, and export job creation.

Sensitive mutation rate limits return the standard error envelope with `429 rate_limited` and a `retry-after` header. Current scoped limits cover login, admin mutations, attachment upload, import job creation, and export job creation.

const formData = new FormData();

Attachment downloads return the stored object bytes and these headers:

- `content-type`: persisted attachment MIME type.
- `content-disposition`: sanitized `attachment; filename="..."` value.
- `content-length`: stored byte length when available.
- `x-request-id`: request correlation ID.

Download model: authorized streaming through Fastify API. The frontend must not use MinIO object keys directly.

### Worker Runtime Contract

Import/export long-running work is backed by the Fastify worker runtime in `apps/api/src/workers/**` and Valkey queue primitives in `packages/cache/src/queue.ts`.

| Queue     | Job type         | Payload                     | Status source              |
| --------- | ---------------- | --------------------------- | -------------------------- |
| `imports` | `import.process` | `{ tenantId, importJobId }` | `GET /api/imports/jobs`    |
| `exports` | `export.verify`  | `{ tenantId, exportJobId }` | `GET /api/reports/exports` |

Worker CLI:

```bash
pnpm worker -- --once --queue imports
pnpm worker -- --once --queue exports
```

Worker behavior:

- Uses Valkey idempotency keys to avoid duplicate enqueue for repeated job creation.
- Import preview and export creation use request fingerprints so repeated keys with changed payloads return `409 idempotency_conflict`.
- Uses Valkey distributed locks while processing a claimed job.
- Retries failed jobs until `maxAttempts`, then moves them to `queue:{name}:dead-letter`.
- Import jobs can be `previewed`, `processing`, `processed`, `failed`, or `dead_letter`. Existing direct processing still returns the preserved `processed` job shape.
- Export worker verifies that the export object exists in MinIO and dead-letters missing-object work after retry exhaustion.
- Frontend should read job status through the list/status APIs, not by reading Valkey directly.

## Frontend Fetch Wrapper Requirements

The frontend should use one shared fetch wrapper with:

```ts
type ApiResult<T> =
  | { ok: true; data: T; requestId?: string }
  | {
      ok: false;
      status: number;
      code: string;
      message: string;
      requestId?: string;
    };
```

Wrapper behavior:

- Always send `credentials: "include"`.
- Add `Accept: application/json` for JSON endpoints.
- Parse JSON when `content-type` includes `application/json`.
- Parse text for `/api/metrics`.
- On `401`, clear local session state and route to `/login`.
- On `403`, show a permission-denied screen or disabled action state.
- On `429`, read `retry-after` and show retry countdown for login or the sensitive mutation being submitted.
- Surface `error.requestId` in support/debug UI.

Example:

```ts
async function apiGet<T>(path: string): Promise<ApiResult<T>> {
  const response = await fetch(path, {
    method: "GET",
    credentials: "include",
    headers: { Accept: "application/json" },
  });
  const requestId = response.headers.get("x-request-id") ?? undefined;
  const body = (await response.json()) as unknown;

  if (!response.ok) {
    const errorBody = body as { error?: { code?: string; message?: string; requestId?: string } };
    return {
      ok: false,
      status: response.status,
      code: errorBody.error?.code ?? "unknown_error",
      message: errorBody.error?.message ?? "Request failed.",
      requestId: errorBody.error?.requestId ?? requestId,
    };
  }

  return { ok: true, data: body as T, requestId };
}
```
